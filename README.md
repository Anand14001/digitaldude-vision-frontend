# Digital Dude CRM — web client

React single-page app for the Digital Dude internal CRM, plus the client portal.
React 18 + Vite + TypeScript, Tailwind, TanStack Query.

The API is a separate project (`../digital-dude-api`) and is deployed
separately. See its [`docs/SPEC.md`](../digital-dude-api/docs/SPEC.md) for what
the system does.

## Setup

```bash
npm install
cp .env.example .env     # VITE_API_URL should point at the API
npm run sync:contract    # pull enums and permission keys from the API
npm run dev              # http://localhost:5173
```

The API must be running (`npm run dev` in `../digital-dude-api`, on port 4001 by
default). Sign in with the seeded administrator.

```

├── lib/
│   ├── api.ts        Axios client: token in memory, single-flight refresh
│   ├── auth.ts       Session store and the permission helpers
│   ├── theme.ts      Light / dark / system
│   └── utils.ts      Formatting — dates, Indian currency, hours, initials
├── types/
│   ├── contract.ts   GENERATED by the API — do not edit
│   └── api.ts        Response shapes this client reads
├── components/
│   ├── ui/           The whole component layer, in one file
│   ├── domain.tsx    Status badges, priority, the stage track
│   ├── ListShell.tsx Filter bar, table card, view toggle
│   └── layout/       App shell, portal shell, notifications, search
├── features/         Cross-screen pieces: task board, composer, comments, files
├── hooks/useList.ts  URL-backed filters, debounced search, pagination
└── pages/            One file per screen; settings/ and portal/ are grouped
```

## How it works

**Authentication.** The access token is held in memory only; the refresh token
is an httpOnly cookie the JavaScript cannot read, so a successful XSS cannot
walk off with a long-lived credential. Concurrent 401s share one refresh call,
because the API rotates refresh tokens and parallel refreshes would invalidate
each other.

**Permissions.** `can('projects.view.all', 'projects.view.assigned')` returns
true if the user holds any of the listed keys, matching how the API's route
guards read. Navigation, buttons and routes are filtered by it — but this only
hides UI. The API is the boundary.

**Theming.** Every colour is a CSS variable defined twice, once on `:root` and
once under `.dark`. Switching themes toggles one class. A small script in
`index.html` applies the stored choice before first paint, so a dark-mode reload
never flashes white. The choice is saved per user on the server, so it follows
them to another device.

**Data fetching.** TanStack Query throughout. Lists keep the previous page
visible while the next loads, and 401/403/404/409 are never retried because the
answer will not change.

**The client portal** is a separate shell under `/portal` with its own
navigation and no staff surfaces. A staff account that lands there is redirected
out, and a portal account that tries a staff route is redirected in.

## Conventions

- **The component layer is the design system.** Spacing, focus rings and both
  themes are decided in `components/ui/index.tsx`, not re-tuned per screen.
- **Status colours live in `components/domain.tsx`**, so one enum never renders
  as two different colours on two screens.
- **List state lives in the URL**, so a filtered view can be shared or
  bookmarked, and changing a filter resets to page one.
- **Workflow colours are user-defined** and therefore inline styles; everything
  else is a Tailwind token.

## Build and deploy

```bash
npm run build     # -> dist/
```

A static bundle. Vercel, Netlify, Cloudflare Pages or any static host works.

- Set `VITE_API_URL` at build time; Vite inlines it, so changing it needs a
  rebuild.
- The host must serve `index.html` for unknown paths, or a refresh on
  `/projects/abc` will 404.
- The API's `WEB_ORIGINS` must list this app's exact origin, and
  `COOKIE_DOMAIN` must be the shared parent domain if the two are on different
  subdomains — otherwise sign-in appears to work and then immediately drops.

Routes are code-split, so the first load carries the shell rather than Settings,
Reports and the portal.

## Keeping in step with the API

After an enum or permission change in the API:

```bash
cd ../digital-dude-api && npm run emit:contract
cd ../digital-dude-web && npm run sync:contract
npm run typecheck
```

Response shapes in `src/types/api.ts` are hand-written and describe only the
fields this client reads, so an additive API change never breaks the build.
